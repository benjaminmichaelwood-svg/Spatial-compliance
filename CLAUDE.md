# Spatial Compliance Tool

## Project Overview
Web-based spatial compliance tool for open pit mining. Takes Vulcan .00t triangulation surface files as input, computes cut/fill conformance solids between surface pairs, classifies them into reporting domains, and produces 3D visualisation and PowerPoint reports. Runs entirely in-browser via WASM — no server, no installation.

## Tech Stack
- **Spatial engine:** Rust compiled to WASM (in-browser compute)
- **Frontend:** React 19 + TypeScript + Vite + Tailwind CSS 3
- **3D viewer:** Three.js via react-three-fiber
- **Charts:** Recharts
- **Reports:** PptxGenJS for PowerPoint generation
- **Hosting:** GitHub Pages (free static site)
- **Password:** Simple session-based gate, hardcoded password "spatial2026"

## Vulcan .00t Format Specification
Fully reverse-engineered and validated (zero delta across 68,259 vertices and 134,906 faces vs OBJ export):
- **All values big-endian**
- **Header:** 128 bytes (0x00–0x7F)
  - Offset 0x48: BE u32 = vertex_count
  - Offset 0x60: BE u32 = triangle_count
- **Vertex data:** starts at offset 0x78
  - Each vertex = 24 bytes: 3 × big-endian f64 (Easting, Northing, RL)
- **Triangle data:** starts immediately after vertices, at offset `0x78 + vertex_count × 24`
  - Each triangle = 24 bytes: 3 × BE u32 (1-indexed vertex indices) + 12 bytes zero padding
- **File size** = 128 + (vertex_count × 24) + (triangle_count × 24) — corrected 2026-09 (Priority 10 session): the previous "− 8-byte overlap" text here didn't match `format::decode_surfaces`'s actual (empirically-validated) `expected_size` formula, which has no such subtraction. Found while writing frontend pre-parse validation against the real formula.
- Note: a compressed "vulZ" format variant exists (magic: ea fb a7 8a 76 75 6c 5a) but is NOT yet supported

## Conformance Domains
### Dig Mode (Cut)
- Planned and Mined (green) — volume in plan, mined this period
- Planned Not Mined (red) — volume in plan, not yet mined
- Mined Not Planned (orange) — volume mined outside the plan
- Mined Before Start (blue) — volume mined before the plan period started
- Preschedule Delay (purple) — behind at start due to actual position vs planned start
- Ahead of Plan (cyan) — mined volume planned for a future period

### Dump Mode (Fill)
- Planned and Dumped, Planned Not Dumped, Dumped Not Planned, Dumped Before Start, Dump Preschedule Delay, Dumped Ahead of Plan

## Key Architecture Decisions
- **No grid-based computation** — uses direct mesh-on-mesh BVH-accelerated boolean operations for exact volumes. Grid sampling does not scale for 20km mine sites.
- **Minimum 2 surfaces required** — user assigns surfaces to roles (Production Start/End, Schedule Start/End, Schedule Future). Only assigned surfaces are used; domains adapt accordingly.
- **Web Worker** — all WASM computation runs off the main thread to keep UI responsive.
- **LOD rendering** — 3 detail levels (full, 25%, 5%) with automatic switching during camera movement.
- **No EdgesGeometry** — causes crashes on large meshes. Use shader-based wireframe or material.wireframe only.

## Performance Targets
- 5 surfaces at 50-100MB each (300K+ triangles per surface)
- Mine sites up to 20km long
- 30+ FPS during orbit/zoom
- No browser freezing on any interaction
- Computation runs in Web Worker with progress bar

## Visual Quality Standard (NON-NEGOTIABLE)

The benchmark for all 3D display output is **Deswik, Vulcan, and Maptek PointStudio**. This tool will be judged by mining engineers who use those packages daily. Output that looks worse than those tools is a failed implementation, even if tests pass.

### Definition of visual failure
- Flat-topped, stepped, or blocky prism solids ("Minescape blocks") — solids MUST follow terrain contours smoothly via per-vertex Z interpolation
- Floating disconnected geometry fragments
- Z-fighting, flickering, or overlapping translucent surfaces obscuring each other
- Geometry that ignores the user's visibility toggles
- Colours or gradients that don't match the legend shown
- Jagged domain boundaries where smooth transitions are expected at this data resolution

### Definition of done for ANY change touching geometry generation or rendering
"Tests pass" is NOT done. Done means:
1. `npm run dev`, load test surfaces from `test-data/` (if present), run conformance
2. Visually inspect the 3D result — screenshot it
3. Confirm the result matches the Deswik/Vulcan/PointStudio standard
4. If you cannot run the dev server or inspect visually, you MUST state this explicitly in your completion report: "NOT VISUALLY VERIFIED". Never claim a visual fix is complete without either verifying it or flagging that you could not.

### Standing rules for geometry code
- Prism/solid construction MUST use per-vertex Z interpolation (BVH lookup per vertex), never flat centroid Z per triangle
- Domain painting applies to production_end surface ONLY — never paint all input surfaces
- Rendering uses indexed BufferGeometry + MeshPhongMaterial. NEVER EdgesGeometry, barycentric wireframe shaders, or LOD copies
- All WASM mesh transfer via flat Float32Array/Uint32Array transferables. NEVER serde/JSON for mesh data
- Raycasting via three-mesh-bvh only
- User visibility toggles are ALWAYS respected — no display mode may override them
- Do not add new display modes/toggles unless explicitly requested by the user

### Visual reference targets
- Solid surfaces: smooth continuous shells hugging terrain, like a Vulcan triangulation solid
- Thickness heatmaps: PointStudio compliance-to-design style — gradient painted on surface, vertical colour bar legend, user-controlled scale
- Lighting: directional + ambient so benches, batters, and slopes read clearly at any zoom

### Automated visual verification
Run `node scripts/visual-check.mjs` (requires `npm run dev` on localhost:5173 and Playwright installed). It launches headless Chromium with SwiftShader (`--use-angle=swiftshader --enable-unsafe-swiftshader --use-gl=angle`), loads test surfaces, runs conformance, and saves screenshots to `visual-check/` (gitignored). Use `PORT=NNNN` to override the dev server port. In CI environments, set `CHROME_PATH` to the Chromium executable.

### Master Priority 6 — Replace EdgesGeometry with a shader-based wireframe
- **Confirmed the violation:** `CreaseEdges` in `Viewer.tsx` called `new THREE.EdgesGeometry(geometry, CREASE_THRESHOLD_DEG)` directly at 3 call sites (surfaces, batched domain groups, reference layers) — banned outright by this file's own standing rule.
- **Replacement approach (the task's first-choice option, not the "full wireframe" fallback):** a barycentric-coordinate wireframe shader gated per-edge by a precomputed crease flag, so only genuine angle-threshold creases draw — not every triangle edge.
  - One CPU pass over the source triangles (`buildCreaseGeometry`, cached via `useMemo` keyed on `geometry`, same caching discipline as the code it replaces) builds face normals and an edge-adjacency map to decide, per triangle-edge, whether the dihedral angle with its neighbor exceeds `CREASE_THRESHOLD_DEG` (boundary edges — used by only one triangle — always count as creases, matching `EdgesGeometry`'s own behavior). The **output is a fixed, bounded size**: exactly 3 vertices per source triangle with a `barycentric` and a `creaseMask` attribute — unlike `EdgesGeometry`, whose output size is an unpredictable fraction of the edge count (the actual "crashes on large meshes" risk).
  - A small custom `THREE.ShaderMaterial` renders the crease lines entirely in the fragment shader (`fwidth`-based anti-aliased barycentric distance-to-edge, each of the 3 components independently gated by `creaseMask` so non-crease edges are forced to never draw) — no `lineSegments` geometry, no CPU-side line generation, no dependency on the base mesh's own (smooth) normals.
  - Reuses the base material's existing `polygonOffset` (pushes the solid surface slightly away from the camera) so the crease overlay — a normal filled-triangle mesh at native depth — renders cleanly on top without its own offset or z-fighting.
  - Added disposal (`useEffect` cleanup) for both the geometry and the material this code creates.
- **Preserved exact prior visual behavior:** `CREASE_THRESHOLD_DEG` (18°) unchanged, edge colors (`EDGE_COLOR_DARK`/`EDGE_COLOR_LIGHT`) unchanged and still reactive to dark/light mode, opacity 0.7 unchanged, and the existing `style.wireframe` visibility toggle unchanged (still just returns `null` when off).

### Master Priority 7 — Wire up the LOD system
- **Confirmed dead code:** `decimateGeometry()` (`web/src/utils/decimation.ts`) had zero call sites anywhere in the app before this change.
- **3 LOD levels, precomputed once per dataset (not per camera check):** LOD 0 = full resolution, LOD 1 = 25% of triangles, LOD 2 = 5% — via a `LOD_RATIOS` constant and a shared `useLodLevel(sphere)` hook, wired into both `SurfaceMesh` and `BatchedDomainGroup`.
  - **Thresholds are relative to each mesh's own bounding-sphere radius, not a fixed meter value** — so the same logic scales correctly from a small test surface to a 20km site: full detail within 1.5× the mesh's radius, 25% within 4×, 5% beyond that.
  - **Movement detection:** the camera's position is compared between throttled checks (every 150ms, not every frame); if it moved more than a tiny fraction of the mesh's radius, the effective LOD is floored at 1 (25%) for 400ms after the last detected movement — even if the camera is close. This is what keeps orbit/pan/zoom responsive; it upgrades back to full detail once the camera genuinely stops (matching OrbitControls' damping settling, not just the discrete drag ending).
  - **`BatchedDomainGroup` decimates each solid individually before batching them into the merged geometry** — this is what keeps `triRanges` (used by `findSolid()` for hover/click attribution) correct at every LOD level: each solid's own reduced triangle count still marks out its own range in the merged buffer.
  - **The shader-based crease overlay (Priority 6) now caches per LOD-level geometry identity** (a `Map` inside `CreaseEdges`, not a single-slot `useMemo`) so switching back and forth between LOD levels doesn't repeatedly rebuild the crease geometry for a level already seen.
  - **LOD is bypassed while the thickness heatmap is painted** on a surface — heatmap vertex colors are computed against the full-resolution vertex layout, and re-deriving per-vertex coloring for each decimated LOD level's different vertex layout was judged out of scope; heatmap review is a deliberate, stationary precision check, not casual navigation.
  - Disposal added for all 3 precomputed geometries (and their BVH bounds trees) per surface/domain group.
- **Known limitation, documented rather than silently accepted:** `SurfaceMesh`'s hover tooltip (`getThicknessAtFace`) looks up thickness via `upload.indices` (the full-resolution index buffer). When a decimated LOD is active and the mesh is far away, a hovered `faceIndex` from the decimated mesh doesn't line up with that buffer, so thickness readout could be inaccurate in that specific state (far + hovering). This is narrow — the "close" case (where precise hover matters most) always renders at full resolution by design — and building full face-index remapping across LOD levels was judged not worth the added complexity for this pass.
- **Visually and behaviorally verified** (dev server + Playwright + headless Chromium/SwiftShader): via a temporary diagnostic (removed before commit) confirmed the full lifecycle across real camera interaction — initial far view correctly selects LOD 2, zooming out from a mid-distance correctly transitions LOD 1→2, zooming back in correctly cycles through 2→1→0 as the camera settles, oscillating between 0 (stationary) and 1 (momentarily "moving" between scroll ticks) exactly as designed. Screenshots at both extremes (very far / very close) rendered cleanly with no page errors, no missing geometry, no crashes.

### Master Priority 10 — Validate files before attempting to parse them
- **Confirmed the current supported list** rather than assuming: `handleFileSelected` only branches on `.json` vs. everything-else-treated-as-binary-.00t — there is no third format, and no extension check at all before this change (any file, `.pdf` included, would be handed straight to the binary `.00t` parser and fail deep inside it).
- **New `web/src/utils/fileValidation.ts`** — `validateSurfaceFile(file)`, run at the very start of `handleFileSelected`, before any parsing begins:
  - Extension check against the confirmed supported list (`.00t`, `.json`).
  - For `.00t`: reads only the first 128 bytes (never the whole file) and checks — file is at least header-sized; `vertex_count`/`triangle_count` at their documented offsets are plausible (non-zero, under 200M — catches garbage bytes being misread as counts); and the declared counts' implied file size (`128 + vertex_count×24 + triangle_count×24`) doesn't exceed the actual `file.size` (catches truncated/corrupt downloads).   - File size: **warns rather than hard-blocks** beyond 500MB (2× the ~250MB target documented elsewhere in this file) — flagged as a judgment call since the exact ceiling may need tuning; the upload still proceeds automatically. Threshold lives in `SIZE_WARNING_BYTES`.
  - All failures/warnings route through the same `ClassifiedError`/`ErrorBanner` UI from Priority 9 — no new UI pattern introduced.

### Master Priority 14 — General undo/redo
- **Scope covered:** `settings` (min volume/thickness), `boundaries` (region add/remove/rename — not the in-progress polygon draw itself), and the `background` (dark/light) toggle — one combined history (a single snapshot per meaningfully-different state), not independent per-field stacks, matching how a person actually thinks about "undo my last change".
- **Deliberately excluded, and why:** surface upload/removal (per the task's own instruction — re-parsing large files as part of an undo stack is expensive, and Priority 11's remove is already a deliberate, confirmed action); conformance results (recomputing on every undo step would be surprising and slow); `mode` — confirmed there is no in-workspace control that changes it once a comparison is created, so there is nothing for a user to undo there; per-domain/per-surface style Maps (color/opacity/wireframe) — a slider drag firing many `onChange` events would flood the history without debouncing, judged not worth the added complexity for this pass.
- **Implementation:** a `useEffect` watching `[settings, boundaries, background]` diffs the new combined snapshot against the last-known one (via a ref) and pushes to an undo stack when they differ — guarded by an `undoRedoInFlight` ref so applying a snapshot via undo/redo doesn't re-record itself as a new change. Capped at 50 entries.
- **Keybindings:** standard OS convention — Ctrl/Cmd+Z (undo), Ctrl/Cmd+Shift+Z or Ctrl+Y (redo) — checked only while **not** actively drawing a polygon, so they never conflict with that tool's own step-back-last-point undo (also Ctrl/Cmd+Z, left completely untouched, per the task's explicit instruction).
- **Visible affordance:** Undo/Redo icon buttons in the workspace header (next to Save/Load Project), each disabled when its stack is empty — not hidden behind keyboard shortcuts alone.
- **Real bug found and fixed before committing**: the first version decided *whether* to act by reading stack length inside a functional `setState` updater (`setUndoStack(stack => { ...side effects like applySnapshot() and setRedoStack()...; return stack.slice(0,-1); })`). React does not guarantee an updater function runs exactly once — it can be re-invoked (e.g. under concurrent-rendering replay) — so those side effects could silently fire more than once. This surfaced as a real, reproducible bug: a second redo click applied the wrong value and left the redo button incorrectly still enabled. Fixed by reading `undoStack`/`redoStack` from the callback's closure (always current, since `useCallback` recreates it when they change) to decide whether to act, keeping every actual state-updater call pure, and calling `applySnapshot` as a plain side effect in the callback body rather than inside any updater.
- **Visually and functionally verified** (dev server + Playwright + headless Chromium/SwiftShader): changed a setting twice, undid twice (once via keyboard, once via button) back to the original default, redid twice (once via keyboard, once via button) forward to the final value — every intermediate value and every button's enabled/disabled state matched expectations exactly, including after the bug fix above. Separately confirmed the polygon-draw tool's own Ctrl+Z is completely unaffected — pressing it while actively drawing left the general-undo value untouched. Screenshot sent to the user.
- `npx tsc --noEmit` and `npx vite build` both pass cleanly.

### Master Priority 15 — Reduce redundant memory copies during surface parsing
- **Traced the full lifecycle** of a surface's bytes from `file.arrayBuffer()` in `App.tsx` through `engineClient.ts`, the worker, and into the WASM parser, checking every point a full copy is made vs. a transfer or a view:
  - `App.tsx` → worker: **already correct.** `workerParseSurface` posts the raw `ArrayBuffer` with `{transfer: [data]}` — a zero-copy transfer, not a structured-clone copy. The `.00t` binary upload path had no redundant copy here before this change.
  - Worker → `App.tsx`: **already correct.** Both `handleParseSurface` and `handleParseSurfaceJson` post the parsed `positions`/`indices` typed arrays back with `{transfer: [...]}`.
  - `wasmModule.parse_surface_flat(data)` (Rust): the JS `Uint8Array` → WASM linear memory copy on the way in, and the WASM `Vec<f32>`/`Vec<u32>` → new JS `Float32Array`/`Uint32Array` copy on the way out (via `js_sys::Float32Array::copy_from`), are **confirmed unavoidable, not redundant** — JS and WASM have separate memory spaces without `SharedArrayBuffer` + threads (Priority 22's territory), so this single boundary-crossing copy each way is the actual cost of using WASM at all, not something introduced by this codebase. The Rust-side `Vec`s are dropped (WASM memory freed) automatically at the end of the function via normal Rust ownership — confirmed no lingering WASM-side allocation after parsing completes.
  - **Real redundant copy found and fixed**: `engine.worker.ts`'s `storedSurfaceBinaries` (raw file bytes, kept after parsing so `Run Conformance` can later re-derive a JSON representation via `getSurfaceJson`) and `storedSurfaceJsons` (that derived JSON, cached on first use) were being **held simultaneously and indefinitely** once a role's JSON was computed — but `getSurfaceJson` always checks `storedSurfaceJsons` *first*, so once that cache is populated, nothing ever reads `storedSurfaceBinaries` for that role again. Fixed: `getSurfaceJson` now deletes the now-redundant binary entry the moment its JSON derivative is cached.
  - `.json` surface uploads (the secondary path — most real usage is `.00t` binary) inherently copy the file's text content via structured clone when posted to the worker, since raw strings aren't Transferable. Accepted as an inherent cost of using JSON as an interchange format for that path; not changed in this pass, and flagged rather than silently left unmentioned.
- **Measured, not assumed**: for the real 80,000-triangle test surfaces used throughout this session, the raw `.00t` binary is 2,889,744 bytes; its derived JSON representation is 3,168,023 bytes (JSON is actually the *larger* of the two here, not dramatically so — the exact ratio will vary by mesh, but the point stands: two representations of the same data were being kept). Confirmed via a temporary diagnostic (removed before commit) that after the first `Run Conformance` on 2 surfaces, `storedSurfaceBinaries` dropped to 0 entries (both freed) while `storedSurfaceJsons` held the cached values; a second `Run Conformance` on the same surfaces produced zero new binary→JSON conversions (cache hit) and touched no binaries (already gone) — the fix behaves exactly as designed with no wasted re-work.

This is a pure memory-management change; no parsing or computation logic was touched.

Caching the flat `positions`/`indices` at upload time instead of raw bytes, and deriving JSON from those directly in JS (the same conversion pattern already used in Priority 12's session restore) would avoid that second Rust-side parse entirely. Left as a follow-up given the correctness bar this task set (byte-for-byte identical output) and the added surface area of touching a currently-working path late in a long session.

### Master Priority 17 — Support compressed vulZ format (STOPPED — actual decompression not implemented; clear detection added instead)
- **Task explicitly authorized stopping**: "if you cannot determine this with reasonable confidence... stop and report what you found rather than guessing at a binary format." Reasonable confidence was not reached for the compression/decoding itself, so **no vulZ parsing or decompression code was written.**
- **What's known** (from this repo's own prior reverse-engineering, documented in the "Vulcan .00t Format Specification" section above): the magic bytes `ea fb a7 8a 76 75 6c 5a` mark a vulZ-variant file. The last 4 bytes (`76 75 6c 5a`) are the ASCII string `"vulZ"`; the leading 4 bytes (`ea fb a7 8a`) don't decode as ASCII and are presumably a binary tag/checksum/version field of some kind, but their exact meaning is unconfirmed.
- **What's missing, and why that blocks implementation**:
  - **No real vulZ sample file exists anywhere in this repository** (checked `test-data/`, searched the full repo for any `.00t` binaries or fixtures — only plain uncompressed `.00t` files are present, both the ones checked into test fixtures historically and the ones this session generated via `cargo run --bin gen-test-surfaces`). Without a real sample, there is nothing to validate a parser against, and the existing uncompressed-format spec was itself only trusted after validating "zero delta across 68,259 vertices and 134,906 faces vs OBJ export" — i.e., this codebase's own standard for "format understood" requires a real file to diff against, which vulZ does not have.
  - **The compression algorithm is unknown.** Nothing in the codebase, CLAUDE.md, or public sources identifies whether "vulZ" wraps zlib/deflate, LZ4, a proprietary Maptek scheme, or something else. Guessing an algorithm and having it "happen to parse" a byte stream without a known-good sample to check output against would risk silently producing wrong vertex/triangle data — a correctness bug that is worse than not supporting the format at all, especially given this tool's core purpose is exact volume computation.
  - **The post-magic-bytes header layout is unknown** — whether vertex/triangle counts sit at the same offsets (0x48/0x60) as the uncompressed format, whether there's a compressed-size vs. uncompressed-size field, whether compression applies to the whole file or just the vertex/triangle payload after an uncompressed header, etc. None of this is derivable from 8 magic bytes alone.
  - **Public research turned up nothing**: web searches for the vulZ magic bytes, "Maptek Vulcan vulZ format", and general terms for a reverse-engineered/documented vulZ format returned Maptek's official (format-silent) product documentation and unrelated reverse-engineering write-ups — no public spec or community reverse-engineering of this specific compressed variant was found.
- **What would unblock this**: a real `.00t` file saved by Vulcan with vulZ compression enabled (ideally paired with the same surface exported uncompressed or to OBJ, mirroring how the uncompressed format was originally validated), OR official Maptek SDK/format documentation describing the vulZ container. Flagging this explicitly per the task's own instruction rather than guessing.
- **What WAS added, scoped narrowly to avoid any format guessing**: detecting the already-known magic bytes (`ea fb a7 8a 76 75 6c 5a`) and failing with a clear, actionable message instead of the confusing generic error a vulZ file previously produced (blindly reading its compressed bytes as if they were the uncompressed layout — typically "Vertex count is zero" or a nonsensical truncation/size mismatch, since compressed bytes at offsets 0x48/0x60 don't mean anything in that format). This is pure detection, not parsing — it decodes nothing about the compressed payload.
  - `crates/spatial-engine/src/format.rs`'s `decode_surfaces` now checks the first 8 bytes against the vulZ magic before doing anything else, returning `"This is a compressed vulZ-format .00t file, which is not yet supported. Re-export or re-save it as an uncompressed .00t file in Vulcan, then try again."` (`decode_surface` delegates to `decode_surfaces`, so both entry points are covered). New test: `rejects_vulz_magic_with_clear_message`.
  - `web/src/utils/fileValidation.ts`'s `validateOot` (already reading the first 128 bytes for its existing checks — see Priority 10) checks the same magic bytes and returns a matching `ClassifiedError` ("This file uses compressed vulZ format...") before the upload ever reaches the WASM parser, so the user sees the specific message immediately rather than a worker round-trip.

### Master Priority 22 — Multithread the WASM compute engine (STOPPED — cross-origin isolation too fragile on this deployment target, per the task's own instruction)
- **Task explicitly required feasibility research before any implementation**, and explicitly said to stop and report if cross-origin isolation proves too fragile. It does — on three independent, compounding fronts, not one easily-mitigated blocker. **No implementation code was written for this item.**
- **Why multithreaded WASM needs cross-origin isolation at all**: `wasm-bindgen-rayon` (the standard way to parallelize a wasm-pack/wasm-bindgen Rust crate like this one) spins up Web Workers that share the WASM linear memory via `SharedArrayBuffer`. Browsers only expose `SharedArrayBuffer` on a page that is "cross-origin isolated", which requires the page's own HTTP response to carry `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` (or `credentialless`).
- **Blocker 1 — this app's deployment target cannot set those headers at all.** This site deploys to **GitHub Pages** (`.github/workflows/deploy.yml`, `actions/deploy-pages`). GitHub Pages is confirmed (checked directly, current as of this research) to have no native mechanism for custom HTTP response headers of any kind — no `_headers` file support (unlike Netlify/Vercel/Cloudflare Pages), no server config, nothing. COOP/COEP genuinely cannot be set the normal way on this host.
- **Blocker 2 — the only known workaround is itself fragile.** The community-standard workaround for exactly this GitHub-Pages situation is `coi-serviceworker` (gzuidhof/coi-serviceworker): a Service Worker that intercepts the page's own responses and re-serves them with COOP/COEP headers injected client-side, forcing one extra reload on first visit for the SW to take effect. Documented, current limitations that apply directly here:
  - It must be served from the app's own origin (not a CDN) as a separate, un-bundled file — doable, but one more piece of deploy-critical infrastructure with its own failure modes (e.g. an SW update/caching bug silently breaking isolation for returning users).
  - Reliability is explicitly described (by the tool's own ecosystem writeups) as "somewhat hacky", with known edge cases where the pattern doesn't take effect, and behavior that's most reliably tested on Chromium-based browsers — cross-browser behavior (Safari/Firefox, and any locked-down corporate browser configurations mining-engineer users may well be on) is a real open question, not a solved one.
  - Every user for whom isolation doesn't take effect (SW blocked or unsupported, an intervening corporate proxy stripping SW registration, private-browsing restrictions, iframe embedding, etc.) must silently and correctly fall back to today's working single-threaded path — meaning this feature, if built, would be **permanent added complexity** (two compute paths to maintain and keep correct forever) for a **benefit only some unknown fraction of users would ever actually receive**, with no way to know that fraction without shipping and measuring in production.
- **Blocker 3 — the Rust toolchain side is still nightly-only, with no sign of stabilizing.** `wasm-bindgen-rayon` requires the Rust **nightly** channel (confirmed current as of this research — WebAssembly thread/atomics support in `std` for `wasm32-unknown-unknown` is still not available on stable), rebuilding the standard library from source via unstable `-Z build-std=panic_abort,std`, and `RUSTFLAGS` enabling `+atomics,+bulk-memory` (usually `+mutable-globals` too). The ecosystem's own guidance is to pin an exact nightly date (e.g. `nightly-2024-08-02` or similar) specifically *because* unpinned nightly is prone to breakage. This repo's toolchain today is plain `stable` (confirmed: `rustup show` in this environment lists only `stable-x86_64-unknown-linux-gnu`, targeting only `wasm32-unknown-unknown`) — adopting a pinned nightly would be a standing maintenance burden (periodic re-validation against a moving target, CI now needs two toolchains or a channel switch, `wasm-pack build` invocations need the unstable flags threaded through) for the entire lifetime of the project, not a one-time cost.
- **Net assessment**: none of these three is individually fatal — a different host with header control would resolve Blocker 1; a team willing to accept nightly Rust and its maintenance cost could absorb Blocker 3; a team comfortable shipping degraded/inconsistent performance across browsers could accept Blocker 2. But **all three stacking on top of each other, for a performance feature whose actual payoff is unmeasured**, is exactly the "too fragile" scenario this task's own instructions anticipated — implementing it now would mean committing this codebase to a nightly Rust toolchain and a hacky client-side header-injection workaround, on the strength of a hoped-for speedup that hasn't been profiled.
- **What would unblock this**: (a) moving deployment off GitHub Pages to a host with native response-header control (Cloudflare Pages, Netlify, Vercel, or a self-hosted server all support this directly, no service-worker hack needed), which removes Blockers 1 and 2 entirely; and/or (b) Rust's wasm32 atomics/threading support stabilizing on the stable channel, removing Blocker 3. Absent either, the honest recommendation is not to build this now. Flagging this explicitly per the task's own instruction rather than shipping a fragile implementation.
- **Not evaluated in depth given the above (moot while blocked)**: how parallelizable `classify_conformance`'s actual hot loops are (the per-triangle classification loop in `classify/mod.rs` is a plausible rayon `par_iter` candidate on paper, since each triangle's classification is independent before the connected-component/shell-building pass), and how it would compose with the wasm-bindgen worker/Transferable architecture already in place (`engine.worker.ts`) — genuinely interesting follow-up questions, but secondary to the infrastructure blocker above.

### Master Priority 22b — Investigate WASM SIMD as a lower-risk speed lever (STOPPED — not implemented, per the task's own conditional instructions)
- **Task's own conditions for stopping were met**: "report your findings before implementing... if so, stop and report" (if SIMD needs nightly) and "implement in the top 1-2 hottest functions only." Research and profiling below show the *language* path is stable (unlike Priority 22's threading), but the actual hot functions aren't a safe, worthwhile fit for a small, isolated SIMD change — so **no SIMD code was written**, matching the spirit of those conditions even though the literal "needs nightly" trigger didn't fire.
- **Step 1 — profiled the real hot path first, per the task's explicit "do not assume, measure"**: added temporary `Instant`-based timers around `classify_conformance`'s three phases (BVH construction, the per-triangle BVH-query loop, and the domain-grouping/connected-components/shell-building pass), ran against the existing `large_surface_conformance_completes` test (~2M triangles, the largest real scenario already in this codebase), then removed the instrumentation — `git diff` confirms `classify/mod.rs` is byte-identical to before. Measured breakdown (single representative run, `--release`):
  - BVH construction: **1.77s** (~5.5%)
  - Per-triangle BVH-query loop ("pass 1" — the `bvh.rs`/`intersect.rs`-adjacent code the task's own hint pointed at): **15.41s** (~48%)
  - Domain grouping + connected-components + shell-building ("pass 2" — `HashMap`-based grouping, `surface_domain_components`'s union-find, `ShellBuilder`'s vertex deduplication): **13.89s** (~43%) — **a genuinely non-obvious finding**: this is nearly as expensive as the BVH-query loop, not a rounding error, and it's real information the task's own hint ("bvh.rs and intersect.rs's per-triangle intersection tests are the likely candidates") didn't anticipate — confirming why the task said to measure rather than assume.
  - (`intersect.rs`'s actual triangle-triangle intersection routines aren't even in `classify_conformance`'s call path at all — they're used by a different pipeline. The measured hot path is BVH point-query + HashMap grouping, not triangle-triangle intersection.)
- **Step 2 — researched the Rust/toolchain side**: confirmed `std::arch::wasm32` SIMD intrinsics (the `simd128` instruction set) **are available on stable Rust** via `-C target-feature=+simd128` or per-function `#[target_feature(enable = "simd128")]` — genuinely different from Priority 22's threading, which needs nightly's unstable `-Z build-std`. This part of the task's premise ("Rust's SIMD support is stable, not experimental") checks out.
- **Step 3 — but the task's proposed safety mechanism doesn't actually work for WASM the way it does for x86, confirmed via research**: on x86, `#[target_feature(enable=...)]` lets one binary contain multiple code paths, dispatched at runtime via `is_x86_feature_detected!` — the CPU just executes whichever path is chosen. **WebAssembly has no equivalent runtime dispatch.** A wasm engine validates and compiles the *entire* module before running anything; if the module contains *any* `simd128` opcode anywhere — even inside one `#[target_feature]`-gated function that's never called on that engine — engines without SIMD support fail with `CompileError: WebAssembly.instantiateStreaming(): Compiling function failed: Invalid opcode 0xfd`, and the **whole app fails to load**, not just that one function. Real safety requires the community-standard `wasm-feature-detect` pattern: compiling and shipping **two separate `.wasm` binaries** (one with `simd128`, one without) and having the JS loader (`wasm.ts`/`engine.worker.ts`) feature-detect at runtime and fetch/instantiate the right one. That's a real, separate piece of infrastructure work — a second build artifact, a build-step change, and loader changes — not a per-function attribute, and materially bigger than "gate 1-2 functions."
- **Step 4 — is there a small win worth that infrastructure cost anyway?** The two dominant measured costs are a poor natural fit for a *small, isolated* SIMD change regardless of the safety-architecture question:
  - The BVH-query loop (~48%) is a **recursive, branch-heavy tree traversal processing one query point at a time** (`SurfaceBvh::query_node` → `point_in_triangle_z`). SIMD accelerates flat, branch-free, uniform per-element work across many independent data points computed together — this is the opposite shape: recursion, early returns, and only ~10 scalar ops per leaf-triangle test. A genuine vectorization here would mean restructuring the traversal to batch multiple query points (or multiple triangles within a leaf) through SIMD lanes together — a real algorithmic redesign, not a "top 1-2 functions" tweak, and one this tool's zero-tolerance-for-wrong-volumes correctness bar makes riskier to get right in one pass.
  - The domain-grouping pass (~43%) is dominated by `HashMap` hashing/insertion and union-find pointer-chasing — **fundamentally not vectorizable**; there's no SIMD instruction set that meaningfully accelerates hash-table probing or graph traversal.
  - The one place that IS a clean, flat, textbook SIMD reduction pattern — the bounding-box min/max computation over each triangle's 3 vertices in `SurfaceBvh::build` (`bvh.rs` lines ~28-39) — is only part of that already-small 5.5% BVH-construction slice. Even a full 2x speedup there is roughly a 2-3% improvement to total run time — real, but not the "genuine, lower-risk speed improvement" this item is meant to capture, and not proportionate to standing up a dual-binary build/feature-detection pipeline to safely ship it.
- **Net assessment**: unlike Priority 22 (three independent blockers), this one is a single, real mismatch — the *stable-language* path is genuinely available, but (a) this codebase's actual hot paths don't suit a small SIMD change without a larger, riskier algorithmic restructure, and (b) doing it *safely* (without risking a hard load failure on any SIMD-incapable browser/device — smart-TV browsers and certain locked-down enterprise browser configurations are the real, documented cases, plausibly relevant to a mining-engineering audience on locked-down corporate machines) requires infrastructure beyond a function-level change. Implementing now would mean either an unsafe blanket `target-feature=+simd128` (silent full-app failure on incompatible browsers, not just a slowdown) or a disproportionate amount of new build/loader infrastructure for a low-single-digit-percent measured win.
- **What would make this worth revisiting**: (a) a genuine need to restructure the BVH query path for other reasons (e.g. batching for a future feature), which could fold in SIMD-friendly batched point-testing as part of that larger change anyway; or (b) `wasm-feature-detect`-style dual-binary shipping becoming justified for other reasons (e.g. once threading — Priority 22 — is revisited on different hosting, since that already requires a more sophisticated loader), at which point the marginal cost of also shipping a SIMD variant drops.
- **No code changes made for this item.** Verified the codebase is unaffected: `cargo test --release --lib` — 76 passed, 0 failed, 2 ignored (unchanged), and `git diff` confirms the temporary profiling instrumentation was fully removed with no trace left in the committed diff.
